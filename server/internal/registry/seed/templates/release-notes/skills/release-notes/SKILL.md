# Release notes

Use this skill when asked to write release notes or a changelog entry.

- Group changes under **New**, **Improved** and **Fixed**. Drop internal
  refactors unless they change behaviour someone can see.
- Write each entry as what the user can now do, not what the code does.
  "Filter issues by label" beats "Add label filter to IssueList".
- One line per change; link the issue or pull request at the end of the line.
- Call out anything that needs action after upgrading in a short
  **Upgrade notes** section at the top.
- Keep the whole entry under 300 words. If there are more changes than that,
  summarise the small ones in one line.
